# 性能审查与复测

本轮聚焦应用执行路径，不改变 `.dnp` 格式、默认缓存预算或桌面生命周期。
测试环境和测量结果见 [VALIDATION.md](../VALIDATION.md)。

## 已优化的热点

| 路径 | 原实现 | 当前实现 |
| --- | --- | --- |
| `integration/rt/dnr.rs` 的 VFS 建树 | 每遇到目录就递归扫描整个扁平索引，约 O(目录数 × 条目数) | 逆序遍历已排序的索引，自底向上组装，每个节点处理一次；仍有 BTreeMap 查找及目录内排序成本 |
| `crates/package/src/cache.rs` 的缓存命中 | 最初为线性扫描，上一轮改为 O(1) 的全局严格 LRU | 按 ZIP index 定位槽位，命中只克隆 Arc 并设置访问标记；CLOCK 仅在插入需要空间时扫描 |
| `integration/deno.patch` 的目录合并 | 每个磁盘条目线性扫描已有条目；metadata 路径还会额外枚举一次磁盘 | HashSet 查重，metadata 路径复用已取得的 ZIP 元数据；每次调用只枚举一次磁盘 |
| `integration/deno.patch` 的同步/异步文件 op | `buf.into_owned().to_vec().into()` 复制已有的独占 Vec | `buf.into_owned().into()` 将独占缓冲区交给 V8；借用数据仍由 `into_owned()` 复制 |

VFS 仍保留目录排序、ZIP 优先、只读和符号链接语义。缓存仍按内容字节数淘汰，
打开的文件句柄通过 `Arc` 保留数据；不因缓存淘汰导致已有读取者的数据失效。
本轮未新增依赖或 unsafe 代码。

## 可重复基准

```sh
# 包索引读取、100 / 10000 个驻留文件下的缓存命中
cargo run --release -p dnr-package --example performance

# 加入真实 runtime 启动与 Deno/Node 目录枚举
DNR_BIN="$PWD/dist/dnr" cargo run --release -p dnr-package --example performance
```

宿主配置 sccache 时保持启用。如果 Cargo 缓存了先前沙箱中的 `rustc -vV` 权限错误，
可以在已获准访问缓存的构建环境中设置 `CARGO_CACHE_RUSTC_INFO=0` 重新探测；这不关闭 sccache。

基准在临时目录生成 Zstd level 6 ZIP，各指标预热一次，记录后续 7 次样本的中位数。
测试数据生成与缓存预填充不计入计时；结束后清理临时文件。

- 索引与启动：2,500 个模拟 npm 包目录，每个 4 个小文件；另有入口及隐式父目录。
  `Package::open` 得到 12,502 个节点。启动计时包含新进程、VFS、V8、模块执行及退出。
- 缓存：预先读取 100 或 10,000 个文件，再通过 `read_index` 循环命中 20,000 次。
  该指标隔离缓存维护成本，不含路径解析、JS API 或文件内容复制。
- 目录合并：10,000 个 ZIP 文件与 5,000 个磁盘文件，其中 2,500 个同名。
  每次样本调用 20 次 Deno `readDirSync` 和 20 次 Node `readdirSync`，校验结果为 12,500 项。
  使用脚本内 `performance.now()`，不把进程启动算进目录枚举时间。

比较前后版本时，对两份源码使用同一个基准程序、相同 release 配置和同一台机器。
这些是暖文件系统缓存下的合成负载，不代表所有应用同比提速，也不代表冷启动或 Linux 实测。
基准不设置硬性耗时断言，以免把系统负载抖动当成正确性失败。

## 整文件读取基准

```sh
python3 scripts/bench-read-file.py --dnr "$PWD/dist/dnr"
# 对照两个使用相同 release 配置构建的原生运行时
python3 scripts/bench-read-file.py --dnr /absolute/path/to/before /absolute/path/to/after
```

脚本使用 `dist/dnc` 生成包含 16 MiB 文件的 Zstd 应用包，也可通过 `--dnc` 指定打包器。
每个样本启动独立进程，先用文件句柄读取一个字节，预热整个 ZIP 条目；计时只包含
随后 8 次同步或异步 `Deno.readFile` 及少量内容校验，不包含打包、进程启动和首次解压。
丢弃一轮预热结果，再取 7 轮中位数；逐轮交替运行时顺序。参数支持
`--size-mib`、`--iterations`、`--samples`。返回值分配及测量期间可能发生的 GC 包含在计时内。

这次优化只移除文件 op 中冗余的第二次整文件复制。对于仍驻留缓存的 S 字节文件，
热缓存二进制读取从两次 S 字节复制减少到一次，相关数据的理论瞬时存活量由约 3S 降到约 2S。
返回后的缓存与一个 JS 结果仍约为 2S；反复创建返回数组的 GC 压力不会消失。
这些是缓冲区大小模型，不是进程 RSS 保证。该次整文件复制优化未修改模块加载、文本读取、首次解压或淘汰策略；后续并行缓存改动见下文。

## 审查后保留的成本

- 不同 ZIP 文件已支持并行解压；同条目命中仍使用短锁，CLOCK 插入/淘汰仍有管理锁。
  命中不获取管理锁，解压、I/O 与同条目等待期间不持有缓存锁。单个文件仍由一个解码器处理；
  单 Worker 顺序读取不会自动并行，异步文件 API 是否调度到独立线程也不由包层改变。
- `read_file_all` 接入 Deno 的 `Cow<[u8]>` 时仍会复制缓存中的 `Arc<[u8]>` 内容；
  文件 op 已直接转移独占缓冲区，不再复制第二遍。JS 返回值仍需与缓存隔离，防止修改数组污染文件。
  模块等只读路径若要保留共享所有权，需要让下游持有 `Arc`，不能将可释放数据的裸切片伪装为静态引用。
- TS 转译和 CJS 分析仍在运行时完成，dnc 仍只打包。没有引入持久转译缓存或改变包内容。
- 桌面 worker 在事件循环已空闲但窗口/托盘仍存活时，保留 10 ms 等待后复查的逻辑。
  改成事件通知需覆盖所有关闭、托盘与退出路径，并测量实际空闲 CPU；本轮未修改生命周期。
- ZIP 读取增加 `BufReader` 的试验在当前负载上未显示收益，已撤回。

## 正确性验证

缓存测试检查 5 种预算、每种 2,000 次访问的数据与字节预算，覆盖命中、淘汰、零字节文件、
超预算文件和持有引用的读取者；不再要求与严格 LRU 逐次选择相同受害者。另有 CLOCK 第二次机会、
确定性的并行解码/热命中、同条目结果和错误合并、panic 唤醒及重试、在途限制和并发淘汰测试。
损坏 CRC 仍按需报错且不进入缓存，修复原文件后可重试成功；路径替换不会改变已打开包的读取对象。
原生回归另覆盖大目录树、前缀相近的目录名、Unicode、空目录、符号链接及两层目录合并。
这些测试与原有的 Node 插件、Worker、TS/CJS、退出等原生测试一并执行。

文件读取另有所有权回归：Deno 同步/异步与 Node 同步/Promise/回调 API 返回的数组可独立修改，
不会影响缓存、原文件或其他读取结果；覆盖空文件、4,097 字节与 2 MiB 文件、并发读取、
磁盘入口、ZIP 入口和包旁磁盘回退。


## 并行解压与 CLOCK 缓存

`reader.rs` 通过 Unix `FileExt::read_at` 实现 `Read + Seek`：每个读取器保存自己的位置，
共享最初打开的 `Arc<File>`。当前 zip 8.6.0 的 `ZipArchive::clone()` 共享中央目录元数据，
未命中时克隆 archive 即可独立解码，不重新解析目录、不重新按路径打开包。仍由 ZIP 库执行
解码与 CRC 校验，保留原来的声明尺寸检查、额外 EOF 读取和懒解压语义。支持当前 macOS/Linux 目标。

`cache.rs` 按 ZIP index 分配固定槽位，槽位状态为 Empty、Loading 或 Ready。命中只获取
对应槽位的短锁，克隆数据 Arc 并设置 referenced；不维护全局访问顺序。Loading 保存独立的
Flight，本轮等待者共享同一结果，包括超预算而不驻留的数据和失败结果。失败释放槽位，
后续调用可重试；展开式 panic 由 RAII 清理并唤醒等待者。进程 abort 不在恢复范围内。

CLOCK 仅保存驻留条目。插入需要空间时，清除 referenced 并给予第二次机会，随后淘汰
未引用条目；最多扫描开始时驻留条目数的两倍。并发访问使本轮找不到足够空间时，返回结果但
跳过驻留，避免无限扫描。内容字节预算仍严格保持；零字节文件的元数据不计入此预算。
淘汰只释放缓存引用，已打开句柄和 Flight 仍持有自己的数据；大块已淘汰数据在管理锁外释放。
锁顺序固定为 CLOCK 管理锁 → 槽位 → Flight；读取者释放槽位后才等待或进入管理路径。

每包在途解压最多 `min(available_parallelism, 8)` 路，同时按条目声明尺寸计量 256 MiB，
与可配置的驻留缓存预算独立。超过在途字节上限的单文件独占执行；许可覆盖解码及结果发布，
同一 Flight 的等待者和缓存命中不占许可。这不是 RSS 上限：解码器、Vec 转 Arc 的短暂复制、
缓存、已打开句柄、等待者持有的完成结果及 JS 数组另占内存。当前调度不承诺严格 FIFO 公平性。

`CacheStats.hits` 只统计驻留命中，`coalesced` 统计加入现有 Flight 的调用，
`decompressions` 保持成功解压次数的口径。计数分散在槽位中，`stats()` 按需汇总，
成本为 O(条目数)，并发读取期间不是所有计数的原子快照；避免在热路径反复查询。

```sh
# 真实 Worker：每项预热一轮，后续七轮中位数，轮流交换前后版本顺序。
python3 scripts/bench-parallel-read.py --dnr /absolute/path/to/before "$PWD/dist/dnr" \
  --keep /tmp/dnr-parallel-fixture
# 同一个包用于隔离 JS/文件 API 成本的 Rust 多线程基准。
cargo run --release -p dnr-package --example parallel -- /tmp/dnr-parallel-fixture/app.dnp
```

默认 16 个 8 MiB 文件，总解压内容 128 MiB，使用固定种子的 16 字符字母表数据和 Zstd level 6。
冷缓存每轮使用新进程/新 Package，工作由 1/2/4/8 个 Worker 或 Rust 线程均分；操作系统文件缓存是暖的。
Worker 已加载后才开始计时，通过文件句柄读取首尾字节触发完整解压和校验，避免整文件 JS 复制
掩盖包层变化。热缓存先预读全部资源，再计时 20,000 次 Worker 文件打开/首尾读取/关闭；
Rust 热缓存指标为 200,000 次 `read_index`，不含文件 API。计时不含打包、索引建立及 Worker 创建，
包含派发、汇合与内容检查；不设耗时断言。真实应用收益还取决于资源大小、并发方式、缓存命中率和内存带宽。


### 本轮实测（2026-09-18）

Apple M3 / 8 核 / 16 GiB，macOS 27.0 ARM64，Rust 1.98.1，release 构建且保留 sccache。
构建和测试结束后独立测量。以下为真实 Worker 的 7 轮中位数（毫秒）：

| Worker 数 | 冷缓存：优化前 | 冷缓存：优化后 | 热缓存：优化前 | 热缓存：优化后 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 173.611 | 171.617 | 75.201 | 70.198 |
| 2 | 172.854 | 89.614 | 48.607 | 45.519 |
| 4 | 173.930 | 52.139 | 35.342 | 34.208 |
| 8 | 175.447 | 49.382 | 39.520 | 34.834 |

旧版冷缓存耗时几乎不随 Worker 数改变，新版 8 Worker 约快 3.55 倍。热缓存的完整文件 API
收益较小，8 Worker 约快 1.13 倍；不能把包层微基准的倍数当作应用整体收益。

同一负载的 Rust 包层基准（热缓存为 200,000 次 index 读取）：

| 线程数 | 冷缓存：优化前 | 冷缓存：优化后 | 热缓存：优化前 | 热缓存：优化后 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 156.209 | 161.336 | 11.446 | 1.663 |
| 2 | 155.873 | 81.648 | 20.612 | 1.639 |
| 4 | 157.047 | 45.837 | 27.496 | 1.431 |
| 8 | 156.219 | 49.169 | 41.188 | 2.027 |

并行加速不保证随线程数线性增长，8 核包括不同性能的核心，也受内存带宽与调度影响。
单线程冷读在两种基准中分别小幅变快/变慢，没有据此宣称单线程解压得到稳定加速。
原有小文件基准中，12,502 节点的 `Package::open` 为 31.720 → 18.152 ms；
100 / 10,000 个驻留文件的 20,000 次命中分别为 1.292 → 0.119 ms、1.258 → 0.132 ms。
位置读取也减少了共享 seek 路径的开销，但这些数值仍只是当前机器上的合成负载。

原生基线是本轮开始前保留的 release 二进制；Rust 基线取 `4467e78` 的未改动包层源码，
与新版使用相同 `parallel.rs`、依赖锁和 release 配置。原始结果与可复用输入在
`dist/validation-parallel-cache/`；完整验证边界见 [VALIDATION.md](../VALIDATION.md)。
